## 第I章 序文

迷路は何千年もの間、人間を魅了してきました。ミノタウロスを閉じ込めるためにダイダロスが建造したというギリシャ神話の伝説的な**クノッソスの迷宮**から、現代のパズル本やビデオゲームに至るまで、迷路は常に神秘・挑戦・巧妙な設計を象徴してきました。コンピュータサイエンスにおいて、迷路生成は単なる遊び以上のものです。それはアルゴリズム、乱数、グラフ理論の実践的な応用なのです。*Prim法*、*Kruskal法*、*再帰的バックトラッカー*など、迷路生成に使われる有名なアルゴリズムのいくつかは、ネットワーク設計やプロシージャル・コンテンツ生成といった実世界の問題にも使われています。興味深いことに、完全迷路（任意の2点間に唯一の経路が存在する迷路）は、グラフ理論における*全域木（spanning tree）*と直接的な関係があります。迷路を——特に可視化して共有できる迷路を——構築することは、コンピュータがいかにして混沌から構造を生み出すのかを探求する素晴らしい方法であり、その過程を楽しむこともできます。

> 「迷宮とは、迷うための場所ではなく、道を見出すための場所である。」
>
> — 詠み人知らず

## 第II章 AIの利用について

### コンテキスト

学習の過程で、AIはさまざまなタスクを支援することができます。AIツールの多様な能力と、それがどのように作業を支援できるかを探る時間を取りましょう。しかし、常に注意深く、結果を批判的に評価してください。コードであれ、ドキュメントであれ、アイデアであれ、技術的な説明であれ、あなたの質問が適切に構成されていたか、生成された内容が正確であるかを完全に確信することはできません。仲間はミスや見落としを避けるための貴重なリソースです。

### 主なメッセージ

- 反復的で退屈なタスクを減らすためにAIを使いましょう。
- コーディングと非コーディングの両方において、将来のキャリアに役立つプロンプトスキルを磨きましょう。
- AIシステムがどのように機能するかを学び、一般的なリスク・バイアス・倫理的問題をよりよく予測し回避できるようにしましょう。
- 仲間と協力することで、技術的スキルと対人スキルの両方を伸ばし続けましょう。
- 完全に理解し、責任を持てるAI生成コンテンツのみを使用しましょう。

### 学習者としてのルール

- AIツールを探求し、その仕組みを理解する時間を取りましょう。それによって倫理的に使用し、バイアスを減らすことができます。
- プロンプトを書く前に、問題についてよく考えましょう——これにより、より明確で、詳細で、適切な語彙を使った関連性の高いプロンプトを書けるようになります。
- AIが生成したものを体系的にチェック・レビュー・疑問視・テストする習慣を身につけましょう。
- 常にピアレビューを求めましょう——自分自身の検証だけに頼らないでください。

### フェーズの成果

- 汎用および領域特化型のプロンプトスキルの両方を伸ばす。
- AIツールを効果的に活用して生産性を高める。
- 計算論的思考、問題解決力、適応力、協調性を強化し続ける。

### コメントと例

- 試験、評価など、本当の理解を示さなければならない状況に定期的に直面するでしょう。準備をし、技術力と対人スキルの両方を伸ばし続けてください。
- 自分の推論を説明し、仲間と議論することは、しばしば理解のギャップを明らかにします。ピアラーニングを優先しましょう。
- AIツールはしばしばあなた固有のコンテキストを欠いており、汎用的な回答になりがちです。あなたと同じ環境を共有する仲間は、より関連性が高く正確な洞察を提供できます。
- AIが最も可能性の高い答えを生成する傾向がある一方で、仲間は代替の視点や貴重なニュアンスを提供できます。彼らを品質チェックポイントとして活用しましょう。

**✓ 良い実践例:**
AIに「ソート関数をどうテストすればいいですか？」と尋ねる。いくつかのアイデアが得られる。それらを試し、仲間とレビューする。一緒にアプローチを洗練させる。

**✗ 悪い実践例:**
AIに関数全体を書かせて、プロジェクトにそのままコピー＆ペーストする。ピア評価の際、それが何をするのか、なぜそうなっているのか説明できない。信用を失い——プロジェクトを不合格になる。

**✓ 良い実践例:**
AIを使ってパーサーの設計を手伝ってもらう。その後、仲間とロジックを一緒に確認する。2つのバグを見つけて一緒に書き直す——より良く、よりクリーンに、そして完全に理解した状態で。

**✗ 悪い実践例:**

### III.1 一般ルール

- プロジェクトは **Python 3.10以降**で書くこと。

- 関数はクラッシュを避けるために例外を適切に処理すること。潜在的なエラーを管理するために try-except ブロックを使用すること。ファイルや接続などのリソースには、自動的なクリーンアップを保証するためコンテキストマネージャを優先すること。レビュー中に未処理の例外によりプログラムがクラッシュした場合、それは動作しないものとみなされます。
- すべてのリソース（ファイルハンドル、ネットワーク接続など）は、リークを防ぐために適切に管理すること。可能な限りコンテキストマネージャを使って自動的に処理すること。
- コードには、関数のパラメータ、戻り値の型、および該当する場合は変数に対して型ヒントを含めること（`typing` モジュールを使用）。静的型チェックには **mypy** を使用すること。すべての関数はエラーなしで mypy を通過しなければなりません。
- 目的・パラメータ・戻り値を文書化するため、PEP 257（Google スタイルまたは NumPy スタイルなど）に従ったdocstringを関数とクラスに含めること。

### III.2 Makefile

一般的なタスクを自動化するために、プロジェクトに **Makefile** を含めること。以下のルールを含んでいなければなりません（必須の lint は指定されたフラグを含みます。より厳格なチェックのために `--strict` を試すことを強く推奨します）:

## 第IV章 必須課題

### IV.1 概要

設定ファイルを受け取り、迷路（場合によっては入口と出口の間に唯一の経路を持つ完全迷路）を生成し、16進数による壁の表現を使ってファイルに書き出すPython製の迷路ジェネレーターを実装します。また、迷路の視覚的表現を提供し、生成ロジックを後から再利用できるようにコードを構成します。

### IV.2 使い方

プログラムは以下のコマンドで実行できなければなりません:

```
python3 a_maze_ing.py config.txt
```

- `a_maze_ing.py` はメインのプログラムファイルです。この名前を使用しなければなりません。
- `config.txt` は唯一の引数です。迷路生成のオプションを定義するプレーンテキストファイルです。ファイル名は別のものを使っても構いません。

プログラムはすべてのエラーを適切に処理しなければなりません：不正な設定、ファイルが見つからない、構文エラー、実現不可能な迷路パラメータなど。予期せずクラッシュすることは決してあってはならず、常にユーザーに明確なエラーメッセージを提供しなければなりません。

### IV.3 設定ファイルの形式

設定ファイルは、1行につき1つの `KEY=VALUE` ペアを含まなければなりません。

`#` で始まる行はコメントであり、無視されなければなりません。

以下のキーは**必須**です:

| キー | 説明 | 例 |
|---|---|---|
| WIDTH | 迷路の幅（セル数） | `WIDTH=20` |
| HEIGHT | 迷路の高さ | `HEIGHT=15` |
| ENTRY | 入口の座標 (x,y) | `ENTRY=0,0` |
| EXIT | 出口の座標 (x,y) | `EXIT=19,14` |
| OUTPUT_FILE | 出力ファイル名 | `OUTPUT_FILE=maze.txt` |
| PERFECT | 迷路が完全迷路かどうか | `PERFECT=True` |

有用であれば、追加のキー（seed、algorithm、display mode など）を加えても構いません。

デフォルトの設定ファイルをGitリポジトリ内に用意しなければなりません。

### IV.4 迷路の要件

- 迷路はランダムに生成されなければならないが、シードによる再現性が必要です。
- 迷路の各セルは、東西南北（北・東・南・西）の各方位に、0〜4個の壁を持ちます。
- 迷路は有効でなければなりません。すなわち:
  - 入口と出口が存在し、互いに異なり、迷路の範囲内にあること。
  - 構造が完全な連結性を保証し、孤立したセルが存在しないこと（後述の「42」パターンを除く）。
  - 入口と出口は特定のセルであるため、外周部には壁がなければならない。
  - 生成されるデータは整合的でなければならない：隣接する各セルは、壁がある場合、同じ壁を持たなければなりません。例えば、あるセルの東側に壁があるのに、その壁の向こう側にある2番目のセルの西側に壁がない、という状態は禁止されます。
- 迷路に大きな開放エリアがあってはなりません。通路は2セルより広くできません。
  例えば、2x3 や 3x2 の開放エリアは可能ですが、3x3 の開放エリアは決して許されません。
- 視覚的に表現されたとき（後述）、迷路には完全に閉じた複数のセルによって描かれた、目に見える「42」が含まれていなければなりません。
- `PERFECT` フラグが有効な場合、迷路は入口と出口の間に**ちょうど1本の経路**を含まなければなりません（すなわち完全迷路：ループが一切ないこと）。
- `PERFECT` フラグが**無効**な場合（デフォルト）、迷路は代わりに**パックマン風のゲームで直接使えるボード**でなければなりません。具体的には:
  - すべての通路が到達可能であること（完全な連結性）。これによりボード全体にパックガムを配置でき、クリア可能な状態が保たれます。
  - 四隅と中央が開いた通路であること（ゴーストとスーパーパックガムは隅に配置され、プレイヤーは中央からスタートします）。
  - **少なくとも2つの独立した経路**（ループ）を提供すること。これにより追われているプレイヤーには常に別の選択肢があります（したがって、完全迷路や、壁を1つだけ取り除いた完全迷路（単一ループ）は、このモードでは**受け入れられません**）。
  - 行き止まりは稀であるべきです（数個は許容されます）。**行き止まりが全くない**ボードが理想的であり、ボーナスとして評価されます（ボーナスの章を参照）。

> 迷路のサイズが小さすぎて「42」パターンを配置できない場合は、省略しても構いません。その場合はコンソールにエラーメッセージを表示してください。

**2つの生成モードの比較（同じグリッド上）:** `PERFECT=True` は1本の曲がりくねった経路を強制します（他のすべての通路は行き止まりになります）。一方、デフォルトの `PERFECT=False` は少なくとも2つの独立した経路を開いたままにするため、追われているプレイヤーには常に代替手段があります。どちらの図でも最短経路がハイライトされています。

### IV.5 出力ファイルの形式

迷路は、1セルにつき1つの16進数の桁を使って出力ファイルに書き出されなければなりません。各桁はどの壁が閉じているかをエンコードします:

| ビット | 方向 |
|---|---|
| 0 (LSB) | 北 |
| 1 | 東 |
| 2 | 南 |
| 3 | 西 |

- 壁が閉じている場合はビットを 1 に、開いている場合は 0 にします。
  例：`3`（2進数 `0011`）は**南**と**西**の壁が開いていることを意味します。あるいは `A`（2進数 `1010`）は**東**と**西**の壁が閉じていることを意味します。
- セルは行ごとに、1行につき1行分が格納されます。
- 空行の後に、以下の3つの要素が3行にわたって出力ファイルに挿入されます:
  - 入口の座標、出口の座標、および入口から出口までの有効な最短経路（`N`、`E`、`S`、`W` の4文字を使用）。
- すべての行は `\n` で終わります。

固有の設定ファイルと組み合わせることで、この出力ファイルは Moulinette によって自動的にテストされる可能性があります。本課題には解析スクリプト（`maze_analyzer.py`）も提供されています。出力ファイルを与えると、壁のエンコーディングが整合的であるか（共有される各壁が両隣のセルで同じ形にエンコードされているか）をチェックし、その迷路が**完全迷路**（`PERFECT=True` で要求される単一経路）なのか、**プレイ可能なボード**（デフォルトで要求される、「42」パターン以外に行き止まりがなく複数の独立経路を持つもの）なのかを報告します。設定ファイルが要求するモードをジェネレーターが生成しているかを確認するために使用できます。

## 第V章 視覚的表現

プログラムは、以下のいずれかを使って迷路を視覚的に表示する手段を提供しなければなりません:

- ターミナルでのASCIIレンダリング、または
- MiniLibX（MLX）ライブラリを使ったグラフィカル表示

視覚表現は、壁・入口・出口・解答経路を明確に示すべきです。

少なくとも以下のタスクについて、ユーザーインタラクションが利用可能でなければなりません:

- 新しい迷路を再生成して表示する。
- 入口から出口への有効な最短経路を表示/非表示する。
- 迷路の壁の色を変更する。
- 任意: 「42」パターンを表示するための特定の色を設定する。

追加のユーザーインタラクションを加えても構いません。

**ターミナルでのデフォルト表示（メニュー例）:**
```
=== A-Maze-ing ===
1. Re-generate a new maze
2. Show / Hide the shortest path
3. Rotate the wall colours
4. Quit
Choice? (1-4): _
```

## 第VI章 コード再利用性の要件

以下の方法を説明する短いドキュメントを提供しなければなりません:

> 迷路ジェネレーターのモジュールは迷路の構造へのアクセスを提供しますが、それは必ずしも出力ファイルと同じ形式である必要はありません。

この再利用可能なモジュール全体（コードとドキュメント）は、後から `pip` でインストールできる単一のファイルとして利用可能でなければなりません。

このパッケージは `mazegen-*` という名前でなければならず、ファイルはgitリポジトリのルートに配置されなければなりません。

Pythonパッケージの標準ビルドによって生成される `.tar.gz` と `.whl` の両方の拡張子が許可されます。

パッケージをビルドするために必要なすべての要素をGitリポジトリ内に用意しなければなりません。これは評価の際に求められます：virtualenv などの環境で、必要なツールをインストールし、ソースからパッケージを再度ビルドします。

## 第VII章 Readmeの要件

Gitリポジトリのルートに `README.md` ファイルを用意しなければなりません。その目的は、プロジェクトに馴染みのない人（仲間、スタッフ、採用担当者など）が、プロジェクトが何についてのものか、どう実行するか、そのテーマについてより詳しい情報をどこで得られるかを素早く理解できるようにすることです。

`README.md` には少なくとも以下を含めなければなりません:

- 一番最初の行はイタリック体で、次のように書かれていること: *This project has been created as part of the 42 curriculum by \<login1\>[, \<login2\>[, \<login3\>[...]]].*
- プロジェクトの目的と概要を含め、プロジェクトを明確に紹介する「**Description**」セクション。
- コンパイル、インストール、実行に関する関連情報を含む「**Instructions**」セクション。
- そのテーマに関連する定番の参考資料（ドキュメント、記事、チュートリアルなど）を列挙し、さらにAIをどのように使用したか——どのタスクで、プロジェクトのどの部分で使ったかを明記した「**Resources**」セクション。

➠ **プロジェクトによっては追加のセクションが必要になる場合があります**（使用例、機能一覧、技術的選択など）。

*必要な追加項目は以下に明示的に列挙されます。*

- 設定ファイルの完全な構造と形式。
- 選択した迷路生成アルゴリズム。
- なぜそのアルゴリズムを選んだのか。
- コードのどの部分が再利用可能で、どのように再利用するのか。
- チームとプロジェクト管理について:
  - 各チームメンバーの役割。
  - 当初の計画と、それが最後までにどう変化したか。
  - うまくいったことと、改善できる点。
  - 特定のツールを使ったか？使ったとすればどれか？

高度な機能（複数のアルゴリズム、表示オプション）を実装した場合は、この `README.md` ファイル内に記述してください。

> 英語が推奨されますが、代わりにキャンパスの主要言語を使用しても構いません。

## 第VIII章 ボーナス

プロジェクトにさまざまなボーナスを追加できます。以下は可能な例です:

- **行き止まりが全くない**デフォルト（非完全）迷路：完全に「編み込まれた（braided）」ボードで、追われるプレイヤーがどこにも閉じ込められないもの（提供されている解析スクリプトが `--max-dead-ends 0` でこれを確認します）。
- 複数の迷路生成アルゴリズムのサポート。
- 迷路生成中のアニメーションの追加。

## 第IX章 提出とピア評価

通常どおり、課題は自分の Git リポジトリに提出してください。評価対象となるのは、あなたのリポジトリ内の成果物のみです。ファイル名が正しいかどうか、遠慮なく再確認してください。

評価の際、**プロジェクトの簡単な修正**を求められることがあります。これには、わずかな挙動の変更、数行のコードの記述や書き直し、あるいは簡単に追加できる機能などが含まれます。

このステップは**すべてのプロジェクトに適用されるわけではありません**が、評価ガイドラインに記載されている場合には、それに備えておかなければなりません。

このステップは、プロジェクトの特定の部分に対するあなたの実際の理解を確認するためのものです。修正は、あなたが選んだ任意の開発環境（普段の環境など）で行うことができ、評価の一部として特定の時間枠が定められていない限り、数分以内に実行可能なものであるべきです。

例えば、関数やスクリプトの小さな更新、表示の変更、新しい情報を格納するためのデータ構造の調整などを求められる可能性があります。

詳細（範囲、対象など）は**評価ガイドライン**に明記され、同じプロジェクトでも評価ごとに異なる場合があります。
